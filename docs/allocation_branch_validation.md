# Episode 24318: controlled allocation validation

This is task validation, not a personalization benchmark. Run four rollouts:
batch/nearest partner x plate/cup robot allocation, no support or history.

```bash
lab-run --new --gpus 1 --cpus 8 bash scripts/run_allocation_branches_partnr.sh
```

Default dataset: data/datasets/partnr_episodes/v0_0/train.json.gz. Override
`habitat.dataset.data_path` if needed. Output limit remains 2048; simulation cap
is 5000 steps. Add `evaluation.save_video=True` for video.

All rollouts reset the episode and seed, then execute Navigate[table_18],
Pick[kettle_0], Navigate[counter_19], Place[kettle_0, on, counter_19, None, None].
Each action must return success before the next. At the next decision boundary,
require empty robot hands, kettle on counter, and both plate/cup unheld and
unfinished. Record the observed state and hash. This is a boundary after prefix
completion, NOT a hard-coded wait until step 424. Its timing is measured.

The selected branch then executes Navigate(source), Pick(object),
Navigate(destination), Place(object). Existing motor tools perform these actions;
no teleportation or forced success. After completion, the ordinary coordination
LLM resumes with the real recent action/results. If a branch skill fails, record
it and release to the LLM for recovery; that run is excluded from the successful
completed-allocation timing comparison. Prefix failure aborts that trial and
records an error; the remaining trials are still attempted.

The prefix and allocation are scripted via the normal planner parser/executor,
not generated by the LLM. robot_decisions.jsonl marks decision_source as
forced_prefix, forced_allocation, or llm. Existing robot_decisions counts include
scripted decisions; do not interpret the aggregate as LLM call count.
branch_audit.json preserves script results, boundary observation and completion
flags even when a run aborts. No profile description or future partner goal is
passed to the robot LLM.

```bash
.venv/bin/python scripts/summarize_allocation_branches.py \
  PATH_TO_COORDINATION/results.jsonl > branch_comparison.json
```

Timing comparisons require successful completed allocations and matching initial
and branch observation hashes within each partner/seed. Positive
steps_saved_by_cup means cup finished sooner. Check the all-trials observed-state
match too before claiming a crossed partner effect. Missing, failed, or truncated
trials remain visible and receive no timing winner. Inspect events and both-agent
failures, not just the winner.

This uses reset + deterministic prefix replay, not a full physics-state snapshot.
Hashes include sim_step and rounded public positions, not all simulator internals.
Equal hashes are a useful check, not proof of exact simulator equivalence. Remaining
LLM choices may differ after the intervention. The result compares these two
allocation-and-continuation trajectories; it does not establish a globally optimal
policy. The terminal public world graph may lag Habitat evaluation, so retain both
task_state_success and raw observations when interpreting final state.
